# MAX Chat · GREEN-API

Тестовое задание на React: минимальный клиент для отправки и получения личных текстовых сообщений в MAX через GREEN-API.

**Онлайн:** [Открыть MAX Chat](https://zhadeanton.github.io/green-api-max-chat/) · **Исходники:** [GitHub](https://github.com/ZhadeAnton/green-api-max-chat)

Для знакомства с интерфейсом нажмите «Посмотреть демо». Для настоящей переписки подключите собственный инстанс MAX по инструкции ниже.

## Локальный запуск

Нужны Node.js **22.12+** (или актуальная LTS) и npm.

```bash
npm ci
npm run dev
```

Откройте **http://127.0.0.1:5173/**. Нажмите **«Посмотреть демо»**, чтобы посмотреть интерфейс без регистрации и ключей. В деморежиме все контакты вымышлены, запросы к GREEN-API не выполняются, ответы генерируются локально.

## Подключение настоящего MAX

1. Создайте **инстанс MAX** в [личном кабинете GREEN-API](https://console.green-api.com/) и авторизуйте его по [инструкции сервиса](https://green-api.com/v3/docs/before-start/). Статус должен быть `authorized`.
2. В настройках инстанса очистите **Webhook URL**, включите **«Получать уведомления о входящих сообщениях и файлах»** (`incomingWebhook: yes`). После изменения настроек подождите около минуты.
3. Для отображения фактических статусов доставки включите `outgoingWebhook: yes`. Для уведомлений об изменениях авторизации включите `stateWebhook: yes`. Они необязательны для базового сценария отправки/получения.
4. В приложении введите `idInstance` и `apiTokenInstance`. Разверните **«Адрес сервера»** и сверьте `apiUrl` с личным кабинетом. По умолчанию стоит `https://3100.api.green-api.com`; для вашего инстанса адрес может быть другим. Адрес не выводится из ID инстанса.
5. Нажмите **«Подключиться»**, затем **«Новый чат»**. Укажите номер получателя в международном формате. Используемый метод MAX `CheckAccount` поддерживает номера России и Беларуси (`+7` и `+375`). Поиск по номеру должен быть разрешён у получателя.
6. Отправьте сообщение. Ответьте с аккаунта получателя в MAX — ответ появится в открытом приложении. Входящие сообщения других собеседников создают отдельные чаты и отмечаются непрочитанными.

Приложение проверяет настройки при подключении и сообщает, что необходимо исправить. Настройки инстанса автоматически не меняются. В браузерах с Web Locks API второй сеанс того же инстанса на этом адресе ждёт завершения первого и не забирает его уведомления. В старых браузерах, на другом адресе приложения или при использовании сторонней интеграции это ограничение нельзя обеспечить: используйте один потребитель `ReceiveNotification` на инстанс.

## Возможности

- React + TypeScript, функциональные компоненты, Vite.
- Подключение по данным пользователя, поиск получателя через `CheckAccount`.
- Отправка через `SendMessage`; текст до 4000 символов, Enter для отправки, Shift + Enter для переноса строки, корректная обработка IME.
- Получение обычного текста и текста со ссылками через HTTP API.
- Один последовательный цикл `ReceiveNotification → обработка → DeleteNotification` на сеанс; смена выбранного чата не перезапускает цикл.
- Web Locks API защищает очередь одного инстанса от одновременного чтения несколькими вкладками приложения.
- При сбое подтверждения повторяется DELETE текущей квитанции. Повторные события не добавляют сообщения дважды.
- Повтор подключения с увеличивающейся задержкой при временных ошибках; отмена запросов и таймеров при выходе.
- Несколько чатов, поиск, фильтр непрочитанных, черновик для каждого чата, мобильная компоновка.
- Состояния отправки, ошибок и неопределённого результата. POST отправки автоматически не повторяется, поскольку при сетевом сбое это могло бы создать дубликат.
- Доступные подписи элементов, фокус в диалогах, управление с клавиатуры и озвучивание новых сообщений.
- Шрифт Manrope поставляется локально вместе с приложением; внешних запросов к Google Fonts нет.

## API и структура

```text
src/
  components/       Экран входа, рабочая область, диалоги и элементы UI
  hooks/            Жизненный цикл сеанса, приём и отправка сообщений
  lib/
    api.ts          Типизированный HTTP-клиент GREEN-API, валидация ответов
    notifications.ts  Преобразование уведомлений в события приложения
    polling.ts      Последовательная очередь, подтверждения, повторы и отмена
    session-lock.ts Доступ к очереди одного инстанса из одной вкладки
    chat-state.ts   Reducer: маршрутизация сообщений, дедупликация, статусы
    demo.ts         Локальная демонстрационная переписка
    format.ts       Номера, даты и форматирование
```

Используется документированный путь `${apiUrl}/waInstance${idInstance}/${method}/${apiTokenInstance}`, в том числе для MAX. Реальный `chatId` запрашивается через `CheckAccount`, чтобы ответы по числовому ID MAX попадали в правильный чат.

GET `ReceiveNotification` использует `receiveTimeout=25`; клиентский таймаут — 35 секунд. Между успешными циклами есть пауза 1 секунда. Временные ошибки повторяются с задержкой от 1,5 до 15 секунд. Ошибки авторизации и конфигурации останавливают цикл до ручного повторного подключения. Все обработанные уведомления, включая неподдерживаемые типы, подтверждаются по `receiptId`, чтобы очередь продвигалась дальше. Групповые чаты, файлы и исходящие эхо-уведомления не отображаются.

Один `useReducer` управляет чатами. Локальные исходящие сообщения получают ID сервера после ответа API; ранние уведомления о доставке сохраняются в ограниченном кэше до получения этого ID. Для подключения используются только HTTPS-хосты API GREEN-API. Серверные ошибки показываются без URL, токенов и необработанного ответа сервера.

## Хранение данных и границы реализации

Ключи, чаты и черновики находятся **только в оперативной памяти вкладки**. `localStorage`, cookies, собственный сервер и база данных не используются. После обновления страницы потребуется подключиться снова, а ранее подтверждённые уведомления не загрузятся повторно. Импорт истории, синхронизация между вкладками, вложения и групповые чаты выходят за рамки этого решения.

Это браузерный клиент: пользователь вводит свой ключ, и браузер отправляет его непосредственно GREEN-API в формате, предусмотренном сервисом. Ключ доступен владельцу браузерной сессии в сетевых инструментах. Для публичного продукта с серверным хранением ключей нужен отдельный backend и управление сессиями. Не добавляйте реальные ключи в исходники, `.env`, скриншоты или запись экрана.

Статус **«Принято GREEN-API»** означает постановку в очередь, а не фактическую доставку. Доставку и прочтение приложение показывает только при получении соответствующих уведомлений. Если результат POST неизвестен, проверьте MAX перед повторной отправкой.

Внешний вид вдохновлён компоновкой MAX Web.

## Проверки

Для TypeScript, TSX и CSS используется [Biome](https://biomejs.dev/): отступы в два пробела, ширина строки 100 символов, единые кавычки и точки с запятой, сортировка импортов, рекомендуемые проверки, доступность React и явные фигурные скобки. `.editorconfig` задаёт единый формат файла для редакторов. Markdown и YAML форматирует Prettier.

```bash
npm run check
npm run format
npm run lint
```

GitHub Actions запускает проверку форматирования и линтер перед сборкой и публикацией.

```bash
npm test
npm run build
npm run preview
```

Vitest проверяет контракт HTTP-клиента на подставных ответах, настройку инстанса, сопоставление номера и chatId, обработку ошибок, последовательность приёма и подтверждения, повтор DELETE, отмену запросов, дедупликацию и гонку между SendMessage и уведомлением статуса.

На Node.js 24.5+ дополнительно выполняются проверки блокировки очереди через нативный Web Locks API: ожидание второго потребителя, отмена ожидающего сеанса и независимость разных инстансов. На более ранних версиях Node эти три проверки пропускаются.

`npm run build` запускает строгую проверку TypeScript и создаёт production-сборку в `dist/`. Предпросмотр production-сборки доступен на **http://127.0.0.1:4173/** после `npm run preview`.

Тесты с подставным API и локальный деморежим не заменяют проверку с двумя настоящими аккаунтами MAX. Для приёмки пройдите шаги подключения выше, отправьте сообщение туда и обратно, затем проверьте переключение чатов и переподключение после потери сети.

## Публикация и сдача

GitHub Pages публикуется автоматически из ветки `main` через `.github/workflows/deploy.yml`. Workflow устанавливает зависимости из lock-файла, собирает проект на Node.js 24 и публикует `dist`. В настройках репозитория **Settings → Pages → Source** выбран **GitHub Actions**. Переменная `GITHUB_PAGES=true` включает путь `/green-api-max-chat/`; локальный запуск продолжает работать по `/`.

Проект можно опубликовать на любом статическом хостинге: команда сборки `npm run build`, каталог публикации `dist`. Серверные переменные окружения для ключей не нужны: каждый пользователь вводит собственные данные в интерфейсе. Приложение использует один URL без серверной маршрутизации.

Для сдачи загрузите исходники в GitHub и приложите ссылку на этот README как инструкцию запуска. Добавьте опубликованную версию (желательно), PDF-резюме с Telegram, а при наличии — скриншоты или видео. Укажите формат работы. Адрес из задания: `hr@green-api.com`; тема: **Тестовое задание на должность - Фронтенд разработчик React**. Письмо не отправляется приложением.
